# Fixly - AI-Powered Repair Guidance

Fixly helps anyone diagnose and fix household problems. Upload a photo of the issue, optionally describe it by typing or speaking, and receive a structured repair guide: problem diagnosis, tools list (essential vs optional), step-by-step instructions, safety notes, and difficulty rating, generated by a local three-model AI pipeline. A case-aware chat assistant answers follow-up questions without the user having to re-explain the problem.

## Completed Phases

### Phase 1 - Core scaffold
- FastAPI project with async SQLAlchemy 2.0 + asyncpg
- PostgreSQL in Docker (`fixly_postgres`, port 5433)
- Alembic migrations for all tables
- Environment variable loading via python-dotenv

### Phase 2 - Authentication
- User registration with bcrypt password hashing
- Login returning a Bearer token stored in the `user_tokens` table
- `get_current_user` FastAPI dependency for all protected routes
- Logout endpoint that invalidates the token server-side

### Phase 3 - Cases (repair sessions)
- Create, list, get, and delete repair cases
- Ownership enforced on all routes
- Cascade delete: removing a case deletes all related uploads, messages, and analyses
- Physical file cleanup on delete

### Phase 4 - File Uploads
- `POST` / `GET` `/api/v1/cases/{case_id}/uploads`
- UUID-based filenames to prevent collisions
- MIME-type allowlist: `image/jpeg`, `image/png`, `image/gif`, `image/webp`
- 10 MB per-file size cap
- Static file serving at `/static/uploads/`

### Phase 5 - Frontend UI (NiceGUI)
- Inter font throughout; Quasar primary overridden to indigo (`#6366f1`)
- Responsive layout: 240 px fixed sidebar on desktop, hamburger + slide-in on mobile
- **Homepage** - dark gradient hero, How It Works section
- **Register / Login** - card-style forms with inline error handling
- **My Cases** (`/cases`) - card list with coloured status stripe, delete, open
- **Case detail** (`/cases/{id}`) - photo grid, lightbox, inline upload widget

### Phase 6 - Cases Dashboard and Upload Pipeline
- My Cases dashboard fully wired to backend
- New case creation flow with photo drag-and-drop + multi-select (up to 10)
- Image upload pipeline from browser to backend to disk
- Photo thumbnails with remove and clear-all actions
- Status badge and case category display

### Phase 7 - AI Pipeline, Chat, and Voice Input

#### Composer UI (`/new` page)
- Single unified composer card: photo area + note textarea + action bar
- Multi-photo selection via native `<label for="file-input">` (no JS `.click()` race)
- Client-side Canvas compression before upload (max 1024 px, JPEG 82%)
- SVG paperclip icon with photo count badge; SVG microphone icon
- Drag-and-drop supported with visual feedback
- Green confirmation banner + thumbnails once photos are attached

#### Voice input
- `MediaRecorder` API records audio in browser (webm/ogg/mp4, whatever the browser supports)
- Audio sent to `POST /api/v1/transcribe` as multipart form data
- Server transcribes with **faster-whisper** (`tiny` model, CPU int8, ~75 MB download on first use)
- Transcribed text appended to the note textarea
- Visual states: idle / recording (red) / transcribing

#### AI Analysis Pipeline (3 stages, all local via Ollama)

| Stage | Model | Task |
|---|---|---|
| 1 | Qwen2.5-VL:3b | Vision - examine images, classify problem, list observations |
| 2 | Mistral:7b-instruct | Planning - list essential tools, optional tools, materials, gear |
| 3 | Llama3.1:8b | Generation - step-by-step repair guide, safety notes, difficulty |

- Images resized to 512 px max before encoding (reduces Stage 1 inference time ~25%)
- `num_ctx=4096` for Stage 1 (critical: prevents mid-JSON truncation on vision calls)
- Graceful Stage 1 fallback: if vision fails, pipeline continues from user's text description
- JSON healing (`_heal_truncated_json`) attempts to recover truncated model output before retry
- Per-stage timing stored in `validation_issues` field for performance monitoring
- Pipeline runs as an `asyncio.create_task` background task - HTTP response is instant (202 Accepted)
- Frontend polls `GET /analysis` every 3.5 s, shows labelled step progress (5-step UI)
- Case title auto-updated from Stage 1 `problem_type` once diagnosis is ready
- Typical total pipeline time: ~97-110 s on CPU-only (no GPU)

#### Analysis result display
- Diagnosis card: problem type, trade category badge, severity badge, visual observations
- Resources section:
  - **Essential** tools and materials (solid indigo bullets)
  - **Nice to have** optional tools and materials (greyed sub-section)
  - Protective gear
  - Estimated time chip
- Step-by-step repair plan: numbered steps with per-step warnings
- Safety notes panel (amber)
- When to call a professional panel (red)
- Metadata footer: total processing time, models used

#### Chat assistant
- Locked until analysis is complete (enforced at both frontend and backend)
- Unlocks **in-place** when analysis finishes - no page reload required
- System prompt anchored to the full case context: problem, trade, tools, steps, safety
- User's original typed question/context passed into the system prompt so the AI answers it directly
- Repair-only scope enforced: off-topic messages are politely redirected
- High-severity cases get an explicit professional recommendation in the system prompt
- Suggestion chips for common starter questions
- Full multi-turn message history persisted in `messages` table

- Python 3.12+
- Docker Desktop (for PostgreSQL)
- [Ollama](https://ollama.com) installed and running

```bash
docker compose up -d db
```

```bash
ollama pull qwen2.5vl:3b
ollama pull mistral:7b-instruct
ollama pull llama3.1:8b
```

### 3 - Backend

```bash
cd backend
python -m venv .venv
# Windows:   .venv\Scripts\activate

pip install -r requirements.txt
alembic upgrade head
python -m uvicorn main:app --host 0.0.0.0 --port 8080
```

Open a second terminal:

```bash
cd frontend
python main.py
```

## Key Design Decisions

**Why three separate models?**
Each pipeline stage is a different cognitive task. Stage 1 needs a multimodal vision model to examine images. Stage 2 is a structured retrieval/planning task well-suited to Mistral's JSON output reliability. Stage 3 is a long-form generation task where Llama 3.1 produces coherent multi-step procedures. Each model can be swapped independently without touching the others.

**Why `asyncio.create_task` instead of `BackgroundTasks`?**
FastAPI's `BackgroundTasks` closes the request DB session when the request ends. The analysis pipeline runs for up to 2 minutes and makes multiple DB writes (one per stage). `create_task` keeps the coroutine alive beyond the request lifecycle with its own session.

**Why `num_ctx=4096` for Stage 1?**
Qwen2.5-VL encodes each image as ~300-700 internal tokens depending on resolution. With a system prompt (~200 tokens) + image tokens + JSON response (~300 tokens), the minimum safe context window is ~1500. The old default of 512 caused every Stage 1 call to truncate mid-JSON. 4096 gives comfortable headroom for up to 3 images.

**Why `<label for="file-input">` instead of `input.click()`?**
Browser security requires file picker invocations to originate from a direct user gesture. A NiceGUI button click goes through a WebSocket round-trip before the Python handler calls `ui.run_javascript("input.click()")` - by then the user gesture context is lost and the browser blocks it. A `<label for="...">` element triggers the file picker natively with no JavaScript required.
